## 🔬 重点论文

### 1. From Runnable to Verifiable: Can Current LLM/Agent-driven Vulnerability Validation Artifacts Really Work?

**类别：漏洞自动化发现/执行类**

**来源：**[arXiv:2608.09567v1](https://arxiv.org/abs/2608.09567)，2026-08-10 提交，领域分类 cs.CR；机构信息：arXiv 摘要页未结构化列出完整机构，未作二级推断。

**入选理由：**这篇论文直接戳中“AI 找洞”落地中最容易被忽略的一层：报告、脚本或 PoC 能跑起来，不等于真的复现了漏洞。它把 LLM/agent 生成或辅助的漏洞验证产物拉回到“可执行”和“可验证”两个硬指标上，适合作为漏洞自动化评测的新基线。

**① 问题是什么：**很多漏洞自动化论文会展示 agent 能生成复现脚本、测试输入、PoC 或补丁验证流程，但真实安全团队关心的是：这份产物能不能在指定环境里稳定运行，并且确实触发目标漏洞。论文指出，“可运行”只说明命令没有立即崩；“可验证”还要求有证据表明触发的是预期漏洞，而不是碰巧崩溃、环境报错或无关异常。

**② 怎么发现的：**作者系统收集了 25 篇 LLM/agent 驱动漏洞验证相关论文中的 251 个产物，然后逐个尝试安装依赖、运行脚本、复现漏洞触发条件，并检查产物是否能被判定为目标漏洞的有效验证证据。摘要披露的关键数字是：只有 33.5% 的产物能执行，只有 19.1% 能真正验证目标漏洞。这说明失败并不是个别仓库维护问题，而是整个研究链条在 artifact 可复现性上的系统性短板。

**③ 挑战机理：**[类型：工程机理 → 可执行环境、漏洞触发条件和漏洞语义证据是三套不同约束，任一层漂移都会让 PoC 从“看似能跑”退化成“无法证明”。] 漏洞验证依赖编译器、操作系统、库版本、服务启动参数、测试输入、崩溃判据和补丁前后差异。LLM 很容易生成语法正确的脚本，但脚本只覆盖命令调用表面；只要目标版本不一致、依赖过期、路径假设错误、触发输入缺失，结果就会变成“跑了但没打中”。这也是为什么普通 benchmark 分数不能直接等价为安全团队可用的复现证据。

**④ 难点是什么：**第一，论文和开源仓库往往只给一段说明，缺少完整容器、镜像、依赖锁定和目标版本。第二，漏洞触发经常需要精确状态，例如特定配置、历史数据、权限、网络交互或竞争条件。第三，验证指标需要区分“目标漏洞触发”和“其他异常”，否则 agent 可能把任意崩溃当作成功。第四，历史漏洞环境会腐化，包仓库、补丁、镜像和上游代码都会随时间变化。

**⑤ 旁路方案：**短期工程上可以先把每个 PoC 放进可重建容器，固定目标版本、依赖版本和触发命令；同时增加补丁前后双环境验证：未打补丁版本应该触发，打补丁版本不应触发。对无法完全复现的漏洞，可以先退到静态证据、最小化输入、调用栈特征和差异测试组合，而不是让 agent 自称“已验证”。

**⑥ 方法是什么：**论文做的是一套面向漏洞验证产物的实证评估框架：收集现有 LLM/agent 论文产物，按可执行性和可验证性分层检查，分析失败原因，并讨论 LLM、RAG 和 agent 在修复复现流程中的作用。它不是再提出一个“更会找洞”的 agent，而是把评测对象从“是否生成答案”转为“是否留下可审计、可复跑、可证明的验证链条”。

**⑦ 方法为什么 work：**因为漏洞验证的核心不是语言生成，而是约束满足：环境约束、版本约束、输入约束、触发路径约束和证据约束必须同时成立。把产物拆成“能否执行”和“能否证明目标漏洞”两层后，很多原本被一句“复现成功”掩盖的问题会暴露出来，也能更清楚地指导 agent 下一步修复环境、修复输入，还是修复判据。

**⑧ 实验怎么开展的：**数据来自 25 篇相关论文的 251 个验证产物；benchmark 是作者构建的漏洞验证产物评估集合；baseline 是现有论文公开产物本身；指标包括可执行率和可验证率。主要结果为 33.5% 可执行、19.1% 可验证。摘要层面未给出完整 baseline 列表、每类漏洞分布、RAG/agent 辅助修复的详细消融和统计显著性，需阅读 PDF 正文进一步核对。

**⑨ 面向的场景：**适合漏洞复现平台、SAST/DAST 误报验证、补丁有效性验证、CVE 回归测试、漏洞赏金初筛、红队 PoC 归档和企业资产上的 one-day 漏洞验证。对安全团队来说，这篇论文的价值在于提醒：AI 生成 PoC 后必须接入证据化验证流水线，而不是直接进入工单或风险评级。

**🔐 网安视角或安全延展：**建议把 agent 生成的每个漏洞结论绑定到最小可复现环境、输入样本、调用栈、补丁前后差异和日志证据上。否则自动化找洞系统会制造大量“看起来专业但无法审计”的风险项，既拖慢修复，也可能在红队环境里误判攻击路径。

### 2. LeanMem: Simple and Efficient Long-Term Memory for LLM Agents

**类别：AI 记忆系统/自进化类**

**来源：**[arXiv:2608.03463v1](https://arxiv.org/abs/2608.03463)，2026-08-04 提交，领域分类 cs.AI、cs.LG；机构信息：arXiv 摘要页未结构化列出完整机构，未作二级推断。

**入选理由：**这篇论文关注的是记忆机制本身：长期任务中 agent 如何把历史交互压缩成可继续使用的记忆。它没有把 memory injection 或 prompt injection 误当成“记忆系统”，而是直接处理写入、压缩和后续复用的问题，符合今日记忆系统类别要求。

**① 问题是什么：**长任务里的 agent 会不断积累观察、用户偏好、失败经验、工具结果和中间计划。如果全部历史都塞回上下文，token 成本、延迟和干扰都会上升；如果粗暴摘要，又可能丢掉后续任务真正需要的细节。LeanMem 要解决的是：如何让 agent 学会把长历史压成短记忆，同时尽量不丢关键决策信息。

**② 怎么发现的：**作者在六个长程任务 benchmark、三类任务设置中比较了完整历史上下文和学习到的紧凑记忆。论文摘要披露：LeanMem 在部分任务中相对完整历史最高提升 7.1%，同时最高把记忆压缩 15.1 倍。这说明“保留所有历史”并不天然最优，因为长上下文里大量无关内容会稀释注意力、增加检索噪声，并让模型在早期错误和后期证据之间摇摆。

**③ 挑战机理：**[类型：系统机理 → 上下文窗口和注意力预算有限，长期记忆必须在信息保真、检索噪声和推理成本之间做压缩取舍。] agent 的历史记录是一个持续增长的序列，而模型每次推理只能处理有限 token。保留越多，计算越贵，干扰越强；删得越多，可能损失关键约束。长期记忆的本质难点不是“有没有数据库”，而是如何学习哪些状态会影响未来动作，哪些只是当时有用但之后可以遗忘。

**④ 难点是什么：**第一，未来任务需要的信息在当前时刻未必显眼，例如用户一句偏好可能几个小时后才影响工具选择。第二，失败经验通常是反事实知识，很难用普通摘要保留，例如“不要再尝试这个 API 参数组合”。第三，短记忆如果写得过抽象，agent 后续无法恢复行动细节；写得过细，又会回到 token 膨胀。第四，不同任务的可遗忘信息不同，规则模板很难通用。

**⑤ 旁路方案：**工程上可以先用人工规则做多层记忆：任务目标和约束长期保留，工具返回值按时间衰减，失败动作写成黑名单，用户偏好进入独立 profile。但这种方案会遇到维护成本和场景迁移问题。LeanMem 的价值在于试图让模型通过训练学会“什么时候该记、记成什么粒度”。

**⑥ 方法是什么：**LeanMem 用强化学习训练 agent 生成紧凑的长期记忆表示。简单说，agent 在任务过程中不断把历史压成较短的记忆文本，后续决策只依赖当前观察和这段记忆；训练奖励同时看任务完成效果和记忆长度，使模型不是单纯追求短，而是学习“短且够用”。

**⑦ 方法为什么 work：**它把记忆写入从人工摘要提示词变成可优化策略：如果某种压缩方式导致后续任务失败，训练信号会惩罚；如果某些细节经常对未来动作有帮助，策略会倾向保留。相比完整历史，紧凑记忆减少了无关 token 对注意力的竞争；相比静态摘要，它能随着任务反馈调整记忆粒度。

**⑧ 实验怎么开展的：**论文摘要说明实验覆盖六个 benchmark、三类长程任务；比较对象包括完整历史上下文和其他记忆设置；指标包括任务表现和记忆压缩率。主要结果是最高 15.1 倍压缩、最高 7.1% 性能提升。摘要未提供六个 benchmark 的完整名称、全部 baseline、消融设置和每项任务的逐项分数，这部分需要以论文正文为准。

**⑨ 面向的场景：**适合客服 agent、代码修复 agent、研究助理、企业知识工作流、长期项目管理 agent 和个人助理。典型例子是代码 agent 连续处理多个 issue 时，需要记住项目约束、失败过的修复路线和测试命令，但不应把每次 shell 输出原样塞回上下文。

**🔐 网安视角或安全延展：**这篇论文本身不是安全攻击论文。安全关联主要在治理层：压缩记忆可能意外删除安全约束、审批记录或用户授权边界，也可能把敏感信息保留得过久。落地时应把安全策略、权限边界、敏感字段和审计日志从普通任务记忆中分离，避免让“省 token”的优化目标覆盖合规要求。

### 3. Order 66: Compositional Threat Analysis of Latent Compromise in LLM Agent Workflows

**类别：AI 安全类**

**来源：**[arXiv:2608.08131v1](https://arxiv.org/abs/2608.08131)，2026-08-08 提交，领域分类 cs.AI、cs.CR、cs.LG；机构信息：arXiv 摘要页未结构化列出完整机构，未作二级推断。

**入选理由：**这篇论文把 agent 安全从单次 prompt injection 扩展到“潜伏式攻陷”：一个看似无害的中间状态、文件、记忆、工具输出或依赖，可能在后续工作流中被组合成真实攻击。它适合归入 AI 安全，因为核心问题是 agent 工作流里的威胁建模和防御切点。

**① 问题是什么：**传统 LLM 安全评测常看模型面对单条恶意指令会不会越权。但真实 agent 工作流更长：它会读文档、调用工具、写文件、复用记忆、引用第三方包、把中间结果交给另一个 agent。攻击者未必需要一次性让模型执行危险动作，只要把恶意状态埋进流程某处，等待后续权限更高的步骤触发即可。

**② 怎么发现的：**作者从 agent 工作流、供应链攻击和真实事件中抽象出“潜伏攻陷”的共同结构：早期步骤只改变上下文或资源，后期步骤在不同权限、不同工具或不同任务目标下执行危险动作。论文提出形式化图模型来描述参与者、资源、工具调用和信任边界，并用它识别攻击路径和最小防御切点。

**③ 挑战机理：**[类型：安全机理 → 局部看起来安全的步骤在组合后可能跨越权限边界，长链路会把上下文污染转化为工具副作用。] 每一步 agent 调用都可能只读一个文件、摘要一段内容或准备一个命令，单独检查不一定违规；但当这些输出被写入记忆、进入检索库、触发自动化脚本或交给高权限工具时，安全属性不再能逐步相加。组合系统的攻击面由路径决定，而不是由单个 prompt 决定。

**④ 难点是什么：**第一，攻击载荷可以延迟触发，扫描当前输入时看不到最终动作。第二，权限可能在多 agent、多工具之间转换，审计日志分散。第三，记忆和检索系统会把旧内容带入新任务，使一次污染影响多次执行。第四，防御太靠前会误杀正常内容，太靠后又可能来不及阻止工具副作用。

**⑤ 旁路方案：**落地系统可以先做低成本控制：每次跨越权限边界时重新确认来源和授权；把外部文档、用户输入、工具输出、长期记忆分成不同信任级别；对会写文件、发网络请求、提交代码、修改权限的工具加执行前策略检查；把 agent 的中间产物记录成证据账本，方便追责和回放。

**⑥ 方法是什么：**论文提出 ACTOR-GRAPH 形式化框架，把 agent、工具、资源、权限和数据流建成图；在图上定义潜伏攻陷路径、组合风险和最小防御 cut set。所谓 cut set，可以理解为“只要在这些边或节点上加控制，就能切断某类攻击链”的最小集合。

**⑦ 方法为什么 work：**图模型能把原本散落在 prompt、工具、记忆和文件系统里的风险统一到路径上看。安全团队不必猜每条恶意指令长什么样，而是分析“哪些数据会流向高权限动作”“哪些节点能改变未来上下文”“哪些边缺少来源校验”。这比只做输入过滤更适合长工作流 agent。

**⑧ 实验怎么开展的：**摘要显示论文以形式化建模、真实事件和供应链攻击链分析为主；没有看到传统机器学习 benchmark、baseline、准确率或消融实验。主要验证方式是用框架解释潜伏攻陷路径，并推导可防守的最小切点。具体案例数量、工具实现和评估细节需以论文正文为准。

**⑨ 面向的场景：**适合企业知识库 agent、代码仓库 agent、CI/CD 自动化 agent、浏览器 agent、采购/财务审批 agent、多 agent 研发流水线和安全运营 agent。凡是“低权限读入内容，高权限执行动作”的系统，都应该把这篇论文的问题模型纳入设计。

**🔐 网安视角或安全延展：**可以把 ACTOR-GRAPH 接到 SOC 和应用安全平台：为 agent 工作流生成数据流图、标注信任边界、识别最短攻击路径，再把高风险边转换成策略，例如二次确认、沙箱执行、输出净化、只读模式、工具白名单和最小权限 token。

### 4. Diagnosing Tool-Selection Reasoning in LLM Agents with Canary Tools

**类别：Agent 类**

**来源：**[arXiv:2608.04719v1](https://arxiv.org/abs/2608.04719)，2026-08-06 提交，领域分类 cs.CL、cs.AI、cs.CY；机构信息：arXiv 摘要页未结构化列出完整机构，未作二级推断。

**入选理由：**工具选择是 agent 能否进入真实业务系统的关键能力。这篇论文没有只看“最后答案对不对”，而是专门诊断模型为什么会在相似工具之间选错，尤其适合评估 MCP、插件、企业工具箱和 coding agent。

**① 问题是什么：**很多 agent benchmark 把工具选择、参数填写和执行结果混在一个总分里。模型答错时，我们不知道它是没理解任务、选错工具、填错参数，还是工具执行失败。论文提出的 canary tools 是“诱饵工具”：它们名字或描述和正确工具很像，但执行后不能完成任务。通过加入这种诱饵，可以专门测 agent 是否真的理解了工具用途。

**② 怎么发现的：**作者构造带 canary tools 的诊断 benchmark，把正确工具旁边放入语义相近的错误工具，然后观察模型选择。摘要指出，工具选择准确率和正确工具、诱饵工具之间的语义相似度呈反向关系：诱饵越像正确工具，模型越容易选错；即使是前沿模型也会受到这种相似性干扰。

**③ 挑战机理：**[类型：数据机理 → 工具描述通常是短文本，模型会用语义相似性近似匹配意图，导致相近工具在表示空间里边界重叠。] 当工具箱越来越大时，很多工具描述只差一个限定词，例如“读取文件”和“读取远端文件”，“发送草稿”和“立即发送”。模型如果主要依赖描述相似度，而没有显式检查前置条件、权限和副作用，就会把“看起来差不多”的工具当成可替代项。

**④ 难点是什么：**第一，真实企业工具箱里的工具命名不一定干净，历史 API、插件和内部系统常有重叠功能。第二，工具描述越短，越难表达边界条件；描述越长，又会增加上下文成本。第三，模型可能在推理文本里说对需求，却在结构化 tool call 中选错。第四，错误工具可能有副作用，例如发错消息、删错文件、查错客户数据。

**⑤ 旁路方案：**工程上可以先做工具分组、权限分层和执行前校验：低风险查询工具允许自动调用，高风险写操作要求确认；相似工具在 schema 中写清“不可用于什么场景”；对高风险工具加入 dry-run 和回滚。还可以让 agent 先输出选择理由，再由策略层检查工具、参数和用户目标是否一致。

**⑥ 方法是什么：**论文提出 Canary Tools 评测方式：在原任务工具集合中插入语义相似但功能不匹配的诱饵工具，控制相似度并观察模型是否被误导。它把 agent 评测从终局结果拆到工具选择阶段，能定位具体失败点。

**⑦ 方法为什么 work：**诱饵工具相当于压力测试模型的“工具边界理解”。如果模型只是根据词面或语义相似度选工具，canary tool 会显著拉低准确率；如果模型真正检查了任务目标、工具前置条件、输出类型和副作用，它就更不容易被诱饵吸走。因此这个 benchmark 能区分“会用工具”和“只是会匹配工具描述”。

**⑧ 实验怎么开展的：**实验围绕带 canary tools 的工具选择任务展开；变量包括正确工具与诱饵工具的语义相似度；指标是工具选择准确率及随相似度变化的退化趋势。摘要披露的主要结论是：准确率与语义相似度负相关，前沿模型也存在相似工具混淆。模型列表、数据规模、baseline、具体数值和消融细节需要阅读论文正文确认。

**⑨ 面向的场景：**适合 MCP 工具生态、浏览器 agent、办公自动化 agent、代码仓库 agent、云平台运维 agent 和安全响应 agent。只要系统允许模型在多个工具中自动选择，这类 canary 诊断就能帮助上线前发现“选错但看似合理”的危险行为。

**🔐 网安视角或安全延展：**攻击者可以故意注册名字相近、描述相近但副作用不同的工具，诱导 agent 调用错误工具。防御上应结合工具签名、来源校验、权限最小化、相似工具冲突检测和高风险调用审计，避免 tool poisoning 演变成数据泄露或越权操作。

## 📢 行业动态

### 1. OpenAI 发布 cyber-critical 能力节奏控制思路

**事件概述：**OpenAI 在 2026-08-18 发布关于“cyber-critical capabilities”时代模型开发节奏的说明，核心是当模型在漏洞发现、漏洞利用链构造等网络能力上接近更高风险门槛时，需要用评测、安全措施和发布节奏控制来维持能力前沿与防护能力之间的间隔。来源：[OpenAI 官方页面](https://openai.com/index/pacing-to-maintain-the-frontier/)。

**为什么重要：**这把 AI cyber 风险从“是否会被滥用”的讨论推进到“模型发布是否需要随能力曲线调速”的治理问题。对做漏洞自动化和安全 agent 的团队来说，未来评测不只看 CTF 分数，还要看真实 exploit chain、未知漏洞推理、自动化复现和防护措施是否同步成熟。

**深层逻辑：**模型能力增长会降低攻击者完成复杂链路的边际成本；而防守侧需要时间建立审计、隔离、红队评测、访问控制和事件响应。如果模型迭代过快，企业和生态安全栈来不及吸收能力变化，就会出现“能力外溢早于防护普及”的窗口。

**下一步推测（推测）：**更可能出现分层发布：普通开发者拿到低风险工具能力，受信任安全团队拿到更强 cyber 模型，前沿漏洞利用能力则需要额外审查、审计和使用约束。

**🔐 网安结合点：**建议安全平台把模型能力评测拆成漏洞发现、PoC 生成、漏洞验证、横向移动规划、权限提升建议等子项，并对每一项设计访问门槛和日志留存。

**可信度提示：**官方来源；具体门槛、模型能力数值和未来发布策略仍需后续官方文件确认。

### 2. OpenAI 提出“防守者窗口”，强调 AI 在安全运营中的部署

**事件概述：**OpenAI 在 2026-08-17 发布《The Defender’s Window》，讨论 AI 如何帮助防守者在漏洞修复、异常检测、代码审查、自动化响应和 agentic pentest simulation 中取得窗口期优势。来源：[OpenAI 官方页面](https://openai.com/index/the-defenders-window/)。

**为什么重要：**这是和上一条相互配套的叙事：一方面承认高能力模型会带来攻击风险，另一方面强调把同类能力尽快装进防守流程。对企业安全团队来说，重点不再是“要不要用 AI”，而是“哪些环节可以先用、哪些动作必须保留人工批准”。

**深层逻辑：**防守长期受制于告警量、资产复杂度、补丁延迟和人才缺口。AI 的优势在于把大量低层分析、上下文整理和候选方案生成自动化，让人类分析师把注意力放在判断、授权和跨团队协调上。

**下一步推测（推测）：**企业会优先把 AI 放进只读和半自动环节，例如告警聚类、日志解释、补丁影响分析、代码审计建议；自动封禁、自动回滚、自动提交生产变更会更慢，因为这些动作的副作用更难接受。

**🔐 网安结合点：**可以围绕“AI 安全运营证据链”做产品化：每条建议必须附资产、日志、检测规则、CVE、补丁状态和可回放推理链，避免安全 agent 只输出一个结论。

**可信度提示：**官方来源；属于方向性文章，不等同于某个具体产品能力已经全部上线。

### 3. Anthropic 与 Chai Discovery 展示 Claude 辅助蛋白设计

**事件概述：**Anthropic 在 2026-08-18 发布研究案例，介绍 Claude 如何帮助 Chai Discovery 的科学团队加速蛋白设计流程，科学家对模型生成设计进行评估。来源：[Anthropic 官方研究页面](https://www.anthropic.com/research/Claude-accelerates-protein-design)。

**为什么重要：**这说明 agent 和大模型正在从文档问答、代码助手进入科学发现工作流。它不是简单聊天，而是嵌入“提出设计、解释候选、由专家筛选、再迭代”的闭环。

**深层逻辑：**科学任务的瓶颈往往不是单次生成答案，而是搜索空间巨大、实验成本高、候选方案需要多轮筛选。大模型在这里更像“候选生成和解释层”，真正闭环还需要领域模型、实验验证和专家判断。

**下一步推测（推测）：**生物、材料和药物研发里的科学 agent 会更强调可追溯性：每个候选设计为什么生成、基于哪些约束、如何被专家否决或保留，都需要进入实验记录。

**🔐 网安结合点：**科学 agent 的安全重点包括实验记录完整性、模型生成候选的来源追踪、敏感知识产权保护，以及对可滥用生物设计能力的访问控制。

**可信度提示：**官方来源；具体实验成功率、湿实验验证范围和可复现材料需要以论文或后续技术报告为准。

## 🧭 今日总体判断

今天的研究主线很清楚：AI 系统不再只比“回答是否漂亮”，而是开始被迫证明“动作是否可验证”。漏洞方向的论文把 PoC 从可运行推进到可验证，agent 方向的 Canary Tools 把最终任务分数拆到工具选择步骤，这两者本质上都在要求模型留下更硬的证据。

记忆系统方向也在往工程真实约束靠拢。LeanMem 代表的趋势不是无限扩大上下文，而是承认长期任务里的历史会变成成本和噪声，必须学习性地压缩、保留和遗忘。未来长期 agent 的竞争点会从“能记很多”转为“知道什么该进入长期记忆，什么只该短期存在，什么必须单独审计”。

AI 安全方向正在从单点攻击转向组合风险。Order 66 的重点不是某条 prompt 多危险，而是低权限输入、长期记忆、检索库、工具调用和高权限动作组合后会产生延迟触发的攻击链。这个判断和 OpenAI 近两天围绕 cyber-critical 能力、defender window 的公开表述是同一条线：能力增长越快，治理就越需要工程化而不是口号化。

行业动态上，OpenAI 同时讲“控制能力发布节奏”和“把 AI 装进防守流程”，这说明前沿模型公司正在把 cyber 视为能力治理的核心场景之一。Anthropic 的蛋白设计案例则显示 agent 化工作流也在科学领域扩展，但科学场景会比办公自动化更依赖可追溯实验记录和专家闭环。

综合看，今天最值得跟的是“证据化 agent”：无论是漏洞验证、工具选择、长期记忆，还是科学设计，系统都必须能回答三件事：为什么这样做、依据来自哪里、失败后能不能回放。只给最终答案的 agent 会越来越难进入高风险业务。

## 🔐 可以和网安结合的研究方向

### 1. PoC 可验证性评分器

**研究问题：**如何自动判断 AI 生成的漏洞 PoC 是否真正触发目标漏洞，而不是只产生无关崩溃或环境错误。

**可行方案：**构建补丁前后双环境、调用栈匹配、崩溃签名、日志证据和最小输入归约的评分器，让 agent 生成 PoC 后必须通过证据检查。

**可用数据或实验方式：**选择有补丁、有测试用例的 CVE；用已知 PoC、LLM 生成 PoC 和人工修改 PoC 做对比；指标包括可执行率、目标漏洞命中率、误报率和复现时间。

**预期价值：**把“AI 说发现漏洞”变成安全团队可审计的验证产物，降低误报工单和不可复现报告。

### 2. 长期记忆的安全约束保真

**研究问题：**agent 压缩长期记忆时，是否会丢失权限边界、用户禁止事项、审计要求和敏感信息处理规则。

**可行方案：**把普通任务记忆和安全约束记忆分层；设计压缩前后约束一致性测试；对“必须保留”的安全事实加不可删除标签和版本记录。

**可用数据或实验方式：**构造长期办公、代码和客服任务，让 agent 在数十轮交互后继续执行高风险动作；测量安全约束遗忘率、错误授权率和敏感字段泄露率。

**预期价值：**让长期记忆 agent 在省 token 的同时不牺牲权限控制和合规审计。

### 3. 相似工具冲突检测

**研究问题：**当 agent 工具箱里存在名字或描述相近的工具时，如何提前发现“容易选错且有副作用”的工具组合。

**可行方案：**计算工具名称、描述、输入输出 schema 和权限范围的相似度；对高相似、高权限差异的工具对生成 canary 测试；上线前要求模型通过工具边界测试。

**可用数据或实验方式：**从 MCP 工具、云 API、办公插件和安全工具中采样真实 schema；插入诱饵工具；指标包括工具选择准确率、误调用率、高风险误调用率和人工确认减少量。

**预期价值：**减少 agent 在企业系统中发错消息、查错数据、删错资源或触发错误安全动作。

### 4. Agent 工作流攻击路径图

**研究问题：**如何在多工具、多记忆、多 agent 工作流中识别潜伏式攻击路径，而不是只过滤单条 prompt。

**可行方案：**把文件、记忆、检索结果、工具调用、权限 token 和输出目标建成图；在图上寻找从不可信输入到高权限动作的路径；对关键边加净化、确认或沙箱。

**可用数据或实验方式：**用代码仓库 agent、浏览器 agent、邮件 agent 和 CI/CD agent 构造攻击场景；比较无图防御、输入过滤、图路径 cut set 防御的成功拦截率和误伤率。

**预期价值：**把 agent 安全从 prompt 规则提升到系统级威胁建模，适合企业内控和红队评估。

### 5. 漏洞复现 agent 的环境自修复

**研究问题：**漏洞验证失败时，agent 如何区分是 PoC 错、环境错、依赖错，还是目标漏洞条件不满足。

**可行方案：**让 agent 生成结构化失败诊断：环境安装、版本确认、触发路径、输入约束、日志证据逐项检查；配合 RAG 检索 README、issue、补丁 diff 和 CVE 描述。

**可用数据或实验方式：**收集历史 CVE 复现仓库，故意注入依赖缺失、版本偏差、配置错误和输入错误；指标包括诊断准确率、自动修复率、最终可验证率和平均迭代次数。

**预期价值：**提升安全团队复现 one-day 和历史漏洞的效率，减少“跑不起来就放弃”的情况。

### 6. 高风险 tool call 的最小授权执行

**研究问题：**agent 什么时候应该被允许自动调用写操作工具，什么时候必须降级为草稿、dry-run 或人工确认。

**可行方案：**按工具副作用、数据敏感性、操作可逆性和用户授权强度建立风险等级；让策略层在模型输出 tool call 后二次裁决，而不是让模型自己决定是否执行。

**可用数据或实验方式：**构造邮件、代码提交、云资源修改、工单关闭、安全封禁等任务；注入相似工具、恶意上下文和不完整授权；指标包括误执行率、阻断率、任务完成率和用户确认成本。

**预期价值：**为企业 agent 上线提供可审计的权限边界，降低工具误用和越权操作风险。

### 7. 科学 agent 的双用途风险审计

**研究问题：**在蛋白设计、材料设计和化学合成等科学 agent 中，如何区分正常研究辅助和潜在双用途滥用。

**可行方案：**将候选生成、约束来源、专家筛选、实验记录和模型建议全部纳入审计；对敏感目标、危险能力和异常查询加访问控制与审批。

**可用数据或实验方式：**使用公开蛋白设计任务和合成路线任务，设置正常目标与高风险目标；指标包括风险识别率、误阻断率、候选可追溯率和专家复核成本。

**预期价值：**让科学发现 agent 能进入真实研发流程，同时降低知识产权泄露和双用途能力外溢风险。
